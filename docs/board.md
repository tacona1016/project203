# BOARD 운영

## 인증과 작성자

사이트 회원 로그인(이름 + 개인 비밀번호)으로 BOARD도 이용합니다. 별도 게시판 비밀번호와 자유로운 이름 변경 기능은 없습니다. `BOARD_PARTICIPANT_PASSWORDS`는 이름을 유지한 사이트 전체 회원 비밀번호 매핑입니다. 회원 세션과 관리자 추가 인증은 [member-auth.md](member-auth.md)를 따릅니다.

모든 글·댓글의 author_id는 검증된 서버 회원 세션에서 결정합니다. 요청의 author_id, participant_id, role, is_admin을 신뢰하지 않습니다. 게시판 세션 GET은 권한 표시만 제공하며 예전 POST 추가 인증은 410으로 종료합니다.

## 권한과 기능

- `/board`: 고정 공지, 최신 글, 제목·본문 검색, 10건 페이지네이션
- `/board/new`, `/board/[id]`, `/board/[id]/edit`: 작성·상세·수정
- 일반 글: 로그인 회원 누구나 작성, 작성자·관리자만 수정/삭제
- 공지·고정·일반/공지 전환: 회원 로그인과 별도 관리자 인증 모두 필요
- 모든 글의 댓글: 회원 작성, 작성자·관리자 삭제, 30건씩 더 보기. 신규 댓글 수정 RPC 적용 후에는 본인 댓글 내용 수정·취소·수정 시각 표시도 지원
- 삭제는 deleted_at만 기록하는 soft delete
- 파일 첨부·웹 사진 업로드는 지원하지 않음. 관리자는 기존 전체 삭제 권한을 유지하지만 다른 회원의 댓글 내용을 대신 수정하지 않음

## 댓글 수정 적용 — 2026-11-02

`supabase/migrations/20261102000000_board_comment_edit.sql`은 검토용 신규 파일이다. 이번 코드 작업에서 운영 DB에 실행하지 않았다. 기존 테이블·데이터·RLS·votes를 변경하지 않고 `edit_board_comment` RPC만 추가하며 서버 역할만 실행할 수 있다.

서버 PATCH `/api/board/posts/<post>/comments/<comment>`는 회원 세션·동일 출처·기존 2,000자 검증 후 세션의 회원 UUID만 RPC에 전달한다. RPC는 부모 게시글 → 활성 회원 → 댓글 순서로 잠그고 본인 작성 여부를 확인한다. 다른 회원 명의·삭제된 글/댓글·비활성 회원은 거부한다. 수정 시 기존 `updated_at` 트리거를 사용한다.

운영 반영 순서는 별도 승인 → 새 SQL만 검토·실행 → 앱 배포 → 실제 권한 확인이다. 과거 schema/seed를 재실행하거나 `supabase db push`로 이력 차이를 덮어쓰지 않는다. 앱을 이전 버전으로 되돌려도 원래 댓글과 RPC는 유지된다. 새 RPC는 미사용 상태로 남겨도 되며 데이터 복원/삭제는 필요 없다. 실제 PostgreSQL 실행·동시성 검증은 별도 TEST DB에서 수행해야 한다.

## 이 기기 임시저장

- 자동 임시저장은 **명시적으로 켠 경우에만** 동작한다. 회원 UUID·새 글/수정 대상·일반/공지별 키로 분리한다. 인증이나 작성자 결정에는 사용하지 않는다.
- 제목·본문·유형·고정 설정만 브라우저 localStorage에 저장한다. 비밀번호·인증 쿠키·서명 키는 저장하지 않는다. 다른 기기와 동기화하지 않는다.
- 마지막 저장부터 7일 후 만료하며 재방문 시 사용자가 ‘임시작성 불러오기’를 선택한다. 복원 전 새 입력을 자동으로 덮어쓰지 않는다. 정상 등록/수정 응답을 받은 뒤 해당 글의 기기 초안을 삭제한다.
- ‘임시저장 삭제’로 스스로 제거할 수 있다. 저장 공간 제한·브라우저 설정 때문에 실패하면 안내한다. 기기 저장은 암호화된 비밀 저장소가 아니므로 공용 기기에서는 사용하지 않는다. 로그아웃하더라도 남은 기기 초안은 만료/삭제 전까지 그 브라우저 저장소에 존재할 수 있다.
- 작성 중 새로고침/브라우저 닫기와 취소 링크에는 내용 유실 확인을 제공한다. 저장한 초안을 사용해도 서버 글은 등록 버튼을 누르기 전까지 생성되지 않는다.

## 탐색·링크·최근 글

검색어와 페이지는 검증한 `/board?q=...&page=...` 목록 주소로만 복귀한다. 외부 URL이나 다른 내부 페이지를 `returnTo`에 넣어도 사용하지 않는다. `NEW`는 작성 후 7일 이내라는 의미이며 읽지 않음 표시가 아니다. 수정만 했다고 NEW 기간을 갱신하지 않는다.

본문·댓글의 HTTP(S) 주소는 안전한 새 탭 링크로 표시하고 HTML/Markdown은 텍스트로 유지한다. 등록된 일반/공지 유형은 그대로 사용하며 ‘프로젝트’ 분류를 위한 DB 컬럼은 추가하지 않았다.

## 최종 의사결정 기록

투표 결과와 최종 합의는 구분한다. 관리자는 기존 공지 작성 화면에서 [결정 기록 템플릿](DECISION_RECORD_TEMPLATE.md)을 복사해 결정일·내용·관련 투표·근거·담당자·다음 행동·일정을 기록할 수 있다. 새 테이블이나 메뉴는 필요 없다. 실제 합의 전에는 확정된 결정처럼 등록하지 않는다.

중요한 현재 결정만 고정하고, 내용이 실질적으로 바뀌면 새 공지를 작성하여 이전 기록과 서로 연결한다. 기존 공지는 수정·soft delete가 가능하므로 변경 불가능한 감사 장부는 아니다. 분기 MDX 정리와 [DB 백업·복구](BACKUP_RESTORE.md)를 함께 운영한다.

작성자·공지 권한은 API와 기존 DB RPC에서 검사합니다. Supabase Secret Key는 서버 전용이며 브라우저 직접 접근 권한과 RLS를 완화하지 않습니다. 기존 participants, polls, votes, comments, board_posts, board_post_comments를 그대로 유지합니다.

## 관련 파일

- `app/board/`, `components/board/`: 화면과 권한 표시
- `app/api/board/`: 글·댓글 API
- `lib/auth/board-session.ts`: 공통 회원 세션으로부터 게시판 작성자·관리자 권한 결정
- `lib/board/`: 입력 검증·타입·DB 작업
- `supabase/migrations/20261023040000_board.sql`: 기존 게시판 스키마 이력
- `supabase/tests/board.sql`: 별도 TEST DB에서만 실행할 DB 권한 회귀 검사

회원 인증 통합을 위해 DB SQL을 다시 실행할 필요는 없습니다. 운영 DB에 기존 schema·seed를 재실행하지 마세요.
