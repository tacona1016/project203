# 로그인 보호 점검 및 운영 적용안

2026-11-01. 이번 작업은 로컬 코드 개선과 운영 적용안 작성까지다. 운영 비밀번호·환경변수·Firewall 설정·DB는 변경하지 않는다.

## 확인한 현재 동작

- 활성 회원 UUID와 개인 비밀번호를 서버에서 확인한 뒤 30일 HttpOnly 회원 쿠키를 발급한다. 비밀번호는 문자열 그대로 비교하며 공유 비밀번호도 허용한다. 길이·문자 조합은 강제하지 않는다. 실제 운영 비밀번호 값이나 중복 여부는 읽지 않았다.
- 회원 비밀번호 변경·매핑 제거·비활성화·서명 키 교체는 기존 세션을 무효화한다. 관리자 인증은 별도 8시간이고 현재 회원 로그인 토큰에 연결된다. 로그아웃/재로그인 후 이전 관리자 인증을 재사용하지 않는다.
- 작성자와 본인 응답 조회는 서버 세션으로 결정한다. 이전 이름 선택·게시판 쿠키·localStorage는 회원 인증 근거가 아니다.
- 인증 실패는 401, 권한/동일 출처 검사 실패는 403, 회원 DB 연결 장애는 503으로 구분한다. DB 장애 때 보호 콘텐츠를 열거나 기존 쿠키를 삭제하지 않는다.
- 애플리케이션의 지속성 있는 로그인 시도 제한은 없다. Vercel의 활성 custom Firewall 설정 읽기는 `404 Config not found`였으며, 규칙 부재·권한·API 접근 차이를 구분할 수 없어 **운영 제한 적용 여부는 미확인**이다.

## 이번 로컬 변경

- 회원/관리자 폼은 HTML 등 비JSON 429 응답에도 재시도 안내를 표시한다. `Retry-After`의 숫자나 HTTP 날짜가 유효한 1~600초 범위일 때만 시간을 표시하고 그 외에는 일반 안내를 사용한다. 응답 원문은 표시하지 않는다.
- 두 폼은 비밀번호 관리자 입력을 FormData로 읽고, 동기 제출 잠금으로 연속 요청을 방지한다. 관리자 폼도 hydration 이전 기본 제출을 막는다. 이는 UX 보호이며 서버의 시도 제한을 대신하지 않는다.
- 보호 응답에 `X-Content-Type-Options: nosniff`와 `X-Frame-Options: DENY`를 추가한다. 이미지 전용 CSP와 비공개 캐시 정책은 그대로 유지한다.
- 회원 비밀번호 정책·세션 기간·UUID·기존 투표 및 게시판 권한은 바꾸지 않는다.

## 승인 후 적용할 1순위: Vercel WAF

새 DB 테이블이나 메모리 카운터 없이 플랫폼의 Fixed Window 제한을 우선 검토한다. 현재 공식 문서상 모든 플랜에서 지원하며 Hobby는 Rate Limiting 1개 규칙, IP/JA4 키 및 지역별 카운터를 사용한다. 최신 한도·비용은 적용 전에 다시 확인한다. [Vercel WAF Rate Limiting](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting)

규칙 초안:

| 항목 | 제안 |
| --- | --- |
| 대상 | `POST /api/access` 또는 `POST /api/admin/access`인 요청을 하나의 OR 규칙으로 묶음 |
| 키 | 플랫폼에서 확인한 IP. 앱에서 IP를 수집·저장하지 않음 |
| 기간/횟수 | 우선 60초에 20회 초안. 실제 로그를 검토하고 승인받아 확정 |
| 초과 동작 | 기본 429. 장기간 계정 잠금은 추가하지 않음 |
| 제외 | 세션 조회·회원 이름 목록·일반 페이지·투표·댓글 요청 |

성공과 실패 모두 카운트된다. 친구 10명이 같은 Wi-Fi에서 동시에 로그인하거나 관리자 인증까지 할 수 있으므로 10회/60초처럼 낮은 값은 정상 요청도 제한할 수 있다. 1~2회 실수로 장시간 잠기지 않도록 짧은 window와 충분한 여유를 둔다. 공유 IP·이동통신 NAT와 지역별 카운터 때문에 실제 사람/계정별 엄격한 제한은 아니다. 여러 지역에서 오는 분산 추측 공격까지 완전히 차단하지 않는다.

### 운영자의 적용 순서

1. Vercel Project → Firewall → Configure에서 기존 규칙·Bypass·프로젝트 플랜을 직접 확인한다. 기존 규칙을 삭제하지 않는다.
2. 위 두 POST 경로를 같은 제한 규칙으로 구성한다. 지원되는 경우 Log 모드로 정상 트래픽 영향과 공유 IP를 먼저 관찰한다. 실제 비밀번호·요청 본문을 별도 로그에 남기지 않는다.
3. 적용 대상, 횟수, 사용량/비용, 로그 보관 범위를 검토하고 승인을 받는다. Save/Draft와 Publish를 구분한다. 이 작업에서는 Draft 생성이나 Publish도 수행하지 않았다.
4. 승인 후 429 적용을 Publish한다. 일반 로그인·관리자 로그인·자동완성, 과도한 요청에서 429, 정상 요청 복구, 투표/댓글이 제한 대상에 포함되지 않는지 확인한다. 운영 검증용 가짜 회원/게시글/투표는 생성하지 않는다.
5. 오탐이 있으면 해당 새 규칙만 비활성화하거나 한도를 조정한다. 비밀번호 초기화·회원 데이터 변경은 필요 없다.

전역적인 계정별 실패 카운터가 추가로 필요해지면 Supabase의 원자적 RPC와 만료 가능한 실패 기록을 별도로 설계할 수 있다. 새 테이블·보관 기간·악의적인 계정 잠금 방지·운영 비용에 대한 승인이 선행돼야 한다. 서버리스 인스턴스 메모리만 사용하는 limiter는 도입하지 않는다.

## 남은 운영 제한

회원별 서로 다른 충분히 긴 비밀번호가 필요하다. 같은 비밀번호를 아는 사람은 다른 이름으로도 로그인할 수 있고, 짧은 비밀번호의 추측 위험은 시도 제한 후에도 남는다. 이번 작업에서는 기존 비밀번호를 변경하거나 강제로 거부하지 않는다. 운영자가 개별 전달 방식으로 교체할 경우 해당 회원은 다시 로그인하며, 다른 회원의 세션과 기존 데이터는 유지된다.

운영 WAF의 현재 상태·실제 제한 동작과 운영 회원 로그인 E2E는 별도 확인 대상이다. 단위/로컬 합성 브라우저 검증과 운영 검증을 구분한다.
